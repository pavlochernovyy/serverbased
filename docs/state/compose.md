# Module composition (`lib/compose.js`)

← [index](./README.md) · API details: [compose.md](../api/compose.md) · see also [open-items.md](./open-items.md)

- `composeModules(...modules)` — accepts any number of `{ handlers?, middlewares?, plugins? }` modules (the exact shape `example/todo-app`, `example/blog-app`, `example/markdown-app`, `example/mini-store` already export) and merges them into one `{ handlers, middlewares, plugins }`, ready to hand to `serverBased()`.
- Handlers are concatenated in module order; a duplicate `method + route` across modules throws `ComposeError` (extends `ServerBasedError`) at composition time — a startup-time failure, not a runtime one, since composition happens before `serverBased(...).run()` is called.
- Middlewares are concatenated in module order too — **no namespacing or scoping**: every module's global middlewares run for every route on the composed app, so a middleware that mutates `res.send` (or anything else globally observable) affects every other module's routes as well.
  - **This bit a real interaction:** `todo-app`'s logging middleware used to unconditionally spread the response body (`{ ...body, logs: 'submitted' }`), which corrupted non-object response bodies from other modules (e.g. `markdown-app`'s plain markdown string got shredded into a character-indexed object). Fixed by having that middleware only tag plain-object bodies and pass anything else through untouched — see `example/todo-app/index.js`. General lesson for any handler/middleware meant to be composable: don't assume every response body in the app is a plain object. Middleware scoping is still unscoped/global today — see [open-items.md](./open-items.md).
- **Plugins are now namespace-checked at compose time**, closing the state-isolation gap this doc used to flag: `composeModules` concatenates each module's `plugins` array (default `[]` if a module doesn't declare any) and throws `ComposeError` if two modules register the same plugin `name` — the same fail-fast-at-startup posture as the duplicate-route check above. A module that wants isolated state should bring its own named plugin (e.g. `mini-store`'s `cart`/`sale`) instead of relying on the shared default `store` plugin (which `serverBased.run()` still auto-injects when no module supplies one — see [core.md](./core.md), "Plugin system"). Modules that *do* rely on the default `store` plugin (e.g. `todo-app` uses key `'todos'`, `blog-app` uses `'posts'`/`'views:<postId>'`) still need distinct key names across each other, same as before.
- `lib/test-fixtures.js` — `createSampleHandler(overrides)`, a shared full-shape handler stub (`route`, `method`, `middleware`, `handlerType`, `run`) used by `lib/handler.test.js` and `lib/compose.test.js` so tests read as realistic handler configs rather than partial `{ route, method }` stubs.
