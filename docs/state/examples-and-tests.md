# Examples and tests

← [index](../README.md)

## Examples

- `example/todo-app` — single config-loaded function (`functions/todo.js`, mounted at `/todo` via `serverbased.json`), full CRUD via `provideState`/`conductState`, route params (`/todo/:todoId`), and the function's own scoped middlewares (logging that rewrites `res.send` for object bodies only, a pass-through "verifying" middleware). Overrides the default `store` plugin with `TodoStorePlugin` (`functions/plugins/todo-store.plugin.js`) — seeded with one todo at construction time, instead of every handler falling back to its own `seedTodos()` on first access.
- `example/blog-app` — single config-loaded function (`functions/blog.js`, mounted at `/posts` via `serverbased.json`) covering posts CRUD plus comments and likes (`/posts/:postId/comments`, `/posts/:postId/likes`, `/posts/:postId/comments/:commentId/likes`). Storage is three independent JSON-file-backed plugins — `postsStore`/`commentsStore`/`likesStore` (`functions/plugins/{blog,comment,like}-store.plugin.js`, all built on the new `lib/plugins/json-store.plugin.js`) — written to and read from `data/*.json` (gitignored), so state survives a process restart; posts seed one entry on first run, comments/likes start empty. Comments/likes reference their parent by a plain id field (`postId`/`commentId`), not a graph/edge syntax. Handlers read/write these stores directly (`context.postsStore`, etc.) rather than through `provideState`/`conductState`, since those only address one plugin literally named `store`. See [context-provider.md#custom-persistence](../api/context-provider.md#custom-persistence-libpluginsjson-storepluginjs) and `example/blog-app/docs/state.md` for the full design/gaps.
- `example/markdown-app` — single config-loaded function (`functions/quote.js`, mounted at `/quote` via `serverbased.json`) rendering markdown via `json2md` from query params, demonstrates per-handler middleware and a function's own module-level `middlewares` (scoped to that function's mount, not global — see `functions/quote.js`'s `cacheMarkdownData`).
- `example/mini-store-app` — a shopping-cart API split (2026-09-11) into two config-loaded functions demonstrating the plugin system (see [context-provider.md](../api/context-provider.md#plugins)): `functions/cart.js` (mounted at `/cart`) brings its own `CartPlugin` (`functions/plugins/cart.plugin.js`) keeping per-cart item state under its own `cart` name, and `functions/sale.js` (mounted at `/sale`) brings its own `SalePlugin` (`functions/plugins/sale.plugin.js`) computing a checkout total with a 10%-off bulk discount for carts with more than 5 items. `/sale/:cartId/checkout` needs `/cart`'s items, which live behind `/cart`'s own plugin isolation — it deliberately reads them over HTTP (`GET /cart/:cartId`) rather than reaching into `/cart`'s plugin directly, same cross-function pattern `example/time-tracking-app/functions/reports.js` uses for `/entries`.
- `example/hello-world-app` (renamed 2026-09-11, was `example/function-registry`) — a `serverbased.json` config plus two function modules: `functions/greet.js` (mounted under its configured `route`, loaded once at startup via `configPath`) and `functions/cart.js` (brings its own named `CartPlugin`, defined in `functions/plugins/cart.plugin.js`, reachable as `context.cart` — demonstrates a function providing its own plugin in-process via context, not HTTP; see [core.md](./core.md)).
- `example/time-tracking-app` — three config-loaded functions via `serverbased.json` — `/entries` (`functions/entries.js`, time-entry start/stop/list), `/projects` (`functions/projects.js`), and `/reports` (`functions/reports.js`). All three use `provideState`/`conductState`, each against an isolated `Map` instance per function (see [core.md](./core.md)): `/entries` and `/projects` each override the default `store` plugin with their own scoped-seed plugin (`EntriesStorePlugin`/`ProjectsStorePlugin`, `functions/plugins/*.plugin.js` — seeds an empty `Map` under their own key at construction, so no per-handler `seedEntries()`/`seedProjects()` fallback is needed), while `/reports` keeps the framework's default `store` plugin (unseeded — its `summaryRequests` counter has no starting value to seed). `/reports/summary` needs `/entries` data that lives in a different, isolated store — it deliberately does *not* reach into that store directly; it calls `/entries`' own route over HTTP instead, demonstrating the intended pattern for cross-function data access (see [open-items.md](./open-items.md) for the isolated-by-default rationale).

## Tests

- `server-based.test.js` — factory defaults and required-field validation (`title`/`purpose`/`version`/`configPath`, each throwing `ServerBasedError` if missing), middleware chaining, JSON/body/query round-trips, route params, per-handler middleware, side-by-side `context` vs `origin` handler types, `provideState`/`conductState` sharing state across requests and handlers within one app instance, custom/overridden plugins, and duplicate-route/duplicate-plugin-name fail-fast checks. Exercises `serverBased({ configPath })` against fixture function modules generated on the fly via `writeFunctionConfig` (`test-fixtures.js`) rather than hard-coded example apps, since `configPath` is the only way to register routes (config-only composition, 2026-09-11).
- `error-handling.test.js` — `RuntimeError` thrown in a `context` handler (sync and async), a plain `Error` defaulting to 500, a malformed-JSON body caught as JSON, and a synchronous throw from an `origin`-type handler. Same `writeFunctionConfig` fixture pattern as `server-based.test.js`.
- `context.provider.test.js` — asserts `ContextProvider` methods are bound and chainable inside a running handler, invoked via a real HTTP request through `serverBased({ configPath })` (a `writeFunctionConfig` fixture).
- `handler.test.js` — asserts `toHandler` normalizes and validates a handler config (via `createSampleHandler` from `test-fixtures.js`).
- `function-registry-config.test.js` — asserts `loadFunctionRegistryConfig` returns `[]` when `configPath` is omitted, missing, or lists no functions (no throw); resolves a function's `path` relative to the config file and loads its `handlers`; passes a function's own `plugins` through `toPlugin`; throws `FunctionRegistryError` on a missing `path`/`route`, two functions sharing a `route`, a duplicate plugin name within one function's own `plugins`, or a duplicate route within one function's own `handlers`.
- `example/hello-world-app/hello-world-app.test.js` — end-to-end: a function listed in `serverbased.json` is reachable over HTTP under its configured `route`; a function's own named plugin (`cart`) is reachable via `context.cart`, in-process, not HTTP; a fresh `run()` call gets a fresh plugin instance (no state leak across app instances); both `greeter` and `cart` functions are reachable on the same running instance; `serverBased(...)` throws a `ServerBasedError` when `configPath` is omitted (required since 2026-09-11).
- `example/time-tracking-app/time-tracking-app.test.js` — asserts the config-loaded `/entries`, `/projects`, and `/reports` functions work together on one server; that all three each hold their own isolated store (writes/reads on one never appear on another, including across a 404); that `/reports/summary` correctly reads `/entries` data across that isolation boundary via an internal HTTP call; and that `/entries`/`/projects` each get a fresh, independently-seeded `EntriesStorePlugin`/`ProjectsStorePlugin` instance per `run()` call.
- `example/todo-app/todo-app.test.js`, `example/blog-app/blog-app.test.js`, `example/markdown-app/markdown-app.test.js`, `example/mini-store-app/mini-store-app.test.js` — API-level tests per example app, real-server/`closeAsync()` pattern. `mini-store-app.test.js` also asserts per-`cartId` isolation within one server and that a fresh `CartPlugin` instance is created per `run()` call (no state leak across server instances). `todo-app.test.js` asserts a fresh, independently-seeded `TodoStorePlugin` instance per `run()` call. `blog-app.test.js` wipes its `data/` dir in `beforeEach` (state now persists to disk across `run()` calls, unlike the other example apps) and covers posts CRUD, comments, likes, 404/400 validation, and — since persistence is the point — that posts and comments survive a `closeAsync()` + fresh `run()` against the same `data/` files.
- No test currently exercises an async rejection from an `origin`-type handler (known unhandled gap, see [core.md](./core.md)) — `ServerBasedError`/`FunctionRegistryError` being thrown during setup *is* covered (`server-based.test.js`, `function-registry-config.test.js`, `example/hello-world-app/hello-world-app.test.js`).

`example/combined-2-apps`, `example/combined-3-apps`, and `example/combined-mini-store-blog` (and their tests) were removed 2026-09-11 as part of the config-only-composition migration — see [`drafts/config-only-composition.task.md`](../drafts/config-only-composition.task.md). What they demonstrated (`composeModules` merging multiple feature modules onto one server) is superseded by every app being a `serverbased.json` + N functions by default.
