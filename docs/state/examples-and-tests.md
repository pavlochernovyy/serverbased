# Examples and tests

← [index](../README.md)

## Examples

- `example/todo-app` — full CRUD via `provideState`/`conductState` (seeded lazily with `seedTodos()`), demonstrates global middlewares (logging that rewrites `res.send` for object bodies only, a pass-through "verifying" middleware) and route params (`/todo/:todoId`). Exports `{ handlers, middlewares }` and only auto-runs when executed directly (`require.main === module`).
- `example/blog-app` — full CRUD via `provideState`/`conductState` (seeded lazily with `seedPosts()`), plus a per-post view counter under a separate state key (`views:<postId>`). Same export/auto-run pattern.
- `example/markdown-app` — single config-loaded function (`functions/quote.js`, mounted at `/quote` via `serverbased.json`) rendering markdown via `json2md` from query params, demonstrates per-handler middleware and a function's own module-level `middlewares` (scoped to that function's mount, not global — see `functions/quote.js`'s `cacheMarkdownData`).
- `example/mini-store` — a shopping-cart API split (2026-09-11) into two config-loaded functions demonstrating the plugin system (see [context-provider.md](../api/context-provider.md#plugins)): `functions/cart.js` (mounted at `/cart`) brings its own `CartPlugin` (`functions/plugins/cart.plugin.js`) keeping per-cart item state under its own `cart` name, and `functions/sale.js` (mounted at `/sale`) brings its own `SalePlugin` (`functions/plugins/sale.plugin.js`) computing a checkout total with a 10%-off bulk discount for carts with more than 5 items. `/sale/:cartId/checkout` needs `/cart`'s items, which live behind `/cart`'s own plugin isolation — it deliberately reads them over HTTP (`GET /cart/:cartId`) rather than reaching into `/cart`'s plugin directly, same cross-function pattern `example/time-tracking-app/functions/reports.js` uses for `/entries`.
- `example/function-registry` — a `serverbased.json` config plus two function modules: `functions/greet.js` (mounted under its configured `route`, loaded once at startup via `configPath`) and `functions/cart.js` (brings its own named `CartPlugin`, defined in `functions/plugins/cart.plugin.js`, reachable as `context.cart` — demonstrates a function providing its own plugin in-process via context, not HTTP; see [core.md](./core.md)).
- `example/time-tracking-app` — combines both approaches in one app: declarative `handlers` (`/entries/*`, time-entry start/stop/list) registered directly in `index.js`, alongside two config-loaded functions via `serverbased.json` — `/projects` (`functions/projects.js`) and `/reports` (`functions/reports.js`). All three use `provideState`/`conductState` against their own default `store` plugin, each an isolated `Map` instance per function/app (see [core.md](./core.md)). `/reports/summary` needs `/entries` data that lives in a different, isolated store — it deliberately does *not* reach into that store directly; it calls the host app's own `/entries` route over HTTP instead, demonstrating the intended pattern for cross-function data access (see [open-items.md](./open-items.md) for the isolated-by-default rationale).

## Tests

- `server-based.test.js` — factory defaults, global middleware chaining, JSON/body/query round-trips, route params, per-handler middleware, side-by-side `context` vs `origin` handler types, and `provideState`/`conductState` sharing state across requests and handlers within one app instance.
- `error-handling.test.js` — `RuntimeError` thrown in a `context` handler (sync and async), a plain `Error` defaulting to 500, a malformed-JSON body caught as JSON, and a synchronous throw from an `origin`-type handler.
- `context.provider.test.js` — asserts `ContextProvider` methods are bound and chainable inside a running handler.
- `handler.test.js` — asserts `toHandler` normalizes and validates a handler config (via `createSampleHandler` from `test-fixtures.js`).
- `compose.test.js` — asserts `composeModules` merges handlers/middlewares in order, tolerates a module with no middlewares, treats the same route as distinct per HTTP method, and throws `ComposeError` on a duplicate method+route across modules.
- `function-registry-config.test.js` — asserts `loadFunctionRegistryConfig` returns `[]` when `configPath` is omitted, missing, or lists no functions (no throw); resolves a function's `path` relative to the config file and loads its `handlers`; passes a function's own `plugins` through `toPlugin`; throws `FunctionRegistryError` on a missing `path`/`route`, two functions sharing a `route`, or a duplicate route within one function's own `handlers`.
- `example/function-registry/function-registry.test.js` — end-to-end: a function listed in `serverbased.json` is reachable over HTTP under its configured `route`; a function's own named plugin (`cart`) is reachable via `context.cart`, in-process, not HTTP; a fresh `run()` call gets a fresh plugin instance (no state leak across app instances); both `greeter` and `cart` functions are reachable on the same running instance; omitting `configPath` boots normally with nothing extra mounted.
- `example/time-tracking-app/time-tracking-app.test.js` — asserts the declarative `/entries` routes and the config-loaded `/projects`/`/reports` functions work together on one server; that `/entries`, `/projects`, and `/reports` each hold their own isolated default `store` (writes/reads on one never appear on another, including across an app-level 404); and that `/reports/summary` correctly reads `/entries` data across that isolation boundary via an internal HTTP call.
- `example/todo-app/todo-app.test.js`, `example/blog-app/blog-app.test.js`, `example/markdown-app/markdown-app.test.js`, `example/mini-store/mini-store.test.js` — API-level tests per example app, real-server/`closeAsync()` pattern. `mini-store.test.js` also asserts per-`cartId` isolation within one server and that a fresh `CartPlugin` instance is created per `run()` call (no state leak across server instances).
- No test currently exercises a `HandlerError`/`ServerBasedError` being thrown during setup, or an async rejection from an `origin`-type handler (known unhandled gap, see [core.md](./core.md)).

`example/combined-2-apps`, `example/combined-3-apps`, and `example/combined-mini-store-blog` (and their tests) were removed 2026-09-11 as part of the config-only-composition migration — see [`drafts/config-only-composition.task.md`](../drafts/config-only-composition.task.md). What they demonstrated (`composeModules` merging multiple feature modules onto one server) is superseded by every app being a `serverbased.json` + N functions by default.
