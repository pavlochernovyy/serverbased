From `docs/audit.txt` and recent design conversations:

- **Validation layer** — explored and drafted (presence-only `validateAgainstSchema`), then explicitly declined for now as too complex for the project's current scale. Not implemented.
- **Mounting composed modules via `app.use(prefix, router)`** instead of flat-merging handlers — discussed as a POC idea (route namespacing "for free", middleware scoped per mount instead of global), postponed. Current composition strategy remains the flat `composeModules` merge — see [compose.md](./compose.md). Worth revisiting alongside the lambda registry below, since a per-mount router is also the natural place to mount/unmount a lambda's routes at runtime.
- **Function registry** — done (2026-09-10, first increment): `configPath` on `serverBased(...)` points at a `serverbased.json` listing independently-authored "functions" (`{ path, route }` per entry), each shaped like today's feature module (`{ handlers, middlewares?, plugins? }`). Read once at startup via `lib/function-registry-config.js`, `require`d in-process, mounted on their own `express.Router()` alongside the app's own `handlers`. Deliberately static: no `fs.watch`, no runtime registry/status API, no process-per-function spawning — enabling/disabling/adding a function means editing `serverbased.json` and restarting. Fails fast at startup on bad entries or route collisions (host-vs-function, function-vs-function), mirroring `composeModules`'s existing duplicate-route check. `runningMode`/`routerEngine` enums remain untouched/unused. See [core.md](./core.md), [server-based.md#function-registry-configpath](../api/server-based.md#function-registry-configpath), `docs/function-registry.task.md` for the design conversation (including the superseded live-filesystem-watch + JSON-API-toggle direction this replaced), and `example/function-registry`.
  - Not designed/started: runtime enable/disable/dismount over an API, live filesystem watching, per-function feature-flag data fields in the config, process-per-function spawning — logged as explicit out-of-scope in `docs/function-registry.task.md`, revisit only as a later increment on top of this static base.
  - **Discovered friction (2026-09-10, `example/time-tracking-app`) — fixed same day:** a function loaded via `configPath` did not get the default `store` plugin auto-appended the way `serverBased()`'s own top-level `handlers` do. Fixed in `run()` (`lib/server-based.js`): each function now gets the same "auto-append `store` unless the function already named its own" treatment the host app gets, with its own fresh `Map` instance per function, per `run()` call — isolated from the host's store and from every other function's store, deliberately (decision below), not shared.
  - **Decision: functions default to an isolated store, on purpose** — each function's default `store` simulates a separate database, the same way a real microservice owns its own database rather than sharing one with its neighbors; `composeModules`-merged feature modules already get isolated plugin instances per `run()` for the same reason (see above). A function that needs another function's (or the host app's) data reads it through that owner's own public HTTP route — see `example/time-tracking-app/functions/reports.js`'s `/reports/summary`, which calls the host app's `/entries` over HTTP rather than reaching into its store — mirroring how a separate service would call another service's API, not its database, keeping the dependency explicit (a network call) instead of a hidden shared-memory reference.
  - See `example/time-tracking-app` for the full pattern: `/entries` (host, declarative `handlers`), `/projects` and `/reports` (both config-loaded functions, each with its own isolated default store), and `/reports/summary` reading `/entries` data across that isolation boundary over HTTP.
- **Per-module middleware isolation** — still not started; global `middlewares` remain unscoped across composed modules (see [compose.md](./compose.md)). The "mounting via `app.use(prefix, router)`" idea above is the most likely path to this, since a per-mount router would scope both routes and middleware together.
- **Plugin constructor arguments** — not started. `run()` always instantiates a plugin as `new Plugin()` with no arguments; a plugin that wants configuration (e.g. `SalePlugin`'s bulk-discount threshold/rate, currently hardcoded constants in `example/mini-store/sale.plugin.js`) has no way to receive it from `serverBased()`'s config today.
- **Plugin type notations** — considered and declined for now: plugins are runtime-injected (`context.<name>`) with no compile-time/type contract describing their shape. Judged acceptable given the startup-time injection mechanics already validate presence (`toPlugin`); revisit only if plugin surfaces grow complex enough that runtime-only discovery becomes error-prone.
- **`run()` startup error handling** — done (2026-09-10): considered switching to a callback-based startup signature, decided against it — `run()` is already awaited/chained everywhere (examples, tests), and a callback would change that call shape for every existing caller. Instead, kept `run()` Promise-based and fixed the actual bug: the server's `'error'` event (e.g. `EADDRINUSE`) now rejects the returned `Promise` instead of leaving it unsettled forever. All `example/*/index.js` entry points were updated to `.catch(...)` the startup call and `process.exit(1)` on failure. See `lib/server-based.js` (`runServerBased`) and [server-based.md](../api/server-based.md).
