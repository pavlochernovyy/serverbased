From `docs/audit.txt` and recent design conversations:

- **[Parked] Mounting composed modules via `app.use(prefix, router)`** instead of flat-merging handlers — discussed as a POC idea (route namespacing "for free", middleware scoped per mount instead of global), postponed. Current composition strategy remains the flat `composeModules` merge — see [compose.md](./compose.md). Full drafted solution and open questions: [`park/router-based-mounting.md`](../park/router-based-mounting.md).
- **Function registry** — done (2026-09-10, first increment): `configPath` on `serverBased(...)` points at a `serverbased.json` listing independently-authored "functions" (`{ path, route }` per entry), each shaped like today's feature module (`{ handlers, middlewares?, plugins? }`). Read once at startup via `lib/function-registry-config.js`, `require`d in-process, mounted on their own `express.Router()` alongside the app's own `handlers`. Deliberately static: no `fs.watch`, no runtime registry/status API, no process-per-function spawning — enabling/disabling/adding a function means editing `serverbased.json` and restarting. Fails fast at startup on bad entries or route collisions (host-vs-function, function-vs-function), mirroring `composeModules`'s existing duplicate-route check. See [core.md](./core.md), [server-based.md#function-registry-configpath](../api/server-based.md#function-registry-configpath), [`drafts/function-registry.task.md`](../drafts/function-registry.task.md) for the design conversation (including the superseded live-filesystem-watch + JSON-API-toggle direction this replaced), and `example/hello-world-app` (renamed 2026-09-11, was `example/function-registry`).
  - **Discovered friction (2026-09-10, `example/time-tracking-app`) — fixed same day:** a function loaded via `configPath` did not get the default `store` plugin auto-appended the way `serverBased()`'s own top-level `handlers` do. Fixed in `run()` (`lib/server-based.js`): each function now gets the same "auto-append `store` unless the function already named its own" treatment the host app gets, with its own fresh `Map` instance per function, per `run()` call — isolated from the host's store and from every other function's store, deliberately (decision below), not shared.
  - **Decision: functions default to an isolated store, on purpose** — each function's default `store` simulates a separate database, the same way a real microservice owns its own database rather than sharing one with its neighbors; `composeModules`-merged feature modules already get isolated plugin instances per `run()` for the same reason (see above). A function that needs another function's data reads it through that owner's own public HTTP route — see `example/time-tracking-app/functions/reports.js`'s `/reports/summary`, which calls `/entries` over HTTP rather than reaching into its store — mirroring how a separate service would call another service's API, not its database, keeping the dependency explicit (a network call) instead of a hidden shared-memory reference.
  - See `example/time-tracking-app` for the full pattern: `/entries`, `/projects`, and `/reports` (all three config-loaded functions, each with its own isolated default store), and `/reports/summary` reading `/entries` data across that isolation boundary over HTTP.
- **[Resolved 2026-09-11] Per-module middleware isolation** — was unscoped global `middlewares` across composed modules; resolved as a side effect of the config-only-composition migration (functions are mounted on their own router with function-scoped `middlewares` — see `docs/drafts/config-only-composition.task.md`), not by the router-based-mounting item below. Full history/analysis: [`park/per-module-middleware-isolation.md`](../park/per-module-middleware-isolation.md).
- **[Postponed, revisit later] Plugin constructor arguments** — not started. `run()` always instantiates a plugin as `new Plugin()` with no arguments; a plugin that wants configuration (e.g. `SalePlugin`'s bulk-discount threshold/rate, currently hardcoded constants in `example/mini-store-app/functions/plugins/sale.plugin.js`) has no way to receive it from `serverBased()`'s config today.
- **Factory validations for data structures `server-based` consumes or provides** — not started. Instead of a compile-time/type contract for plugin shapes, the plan is a runtime **factory** that validates a data structure's expected shape at the point it's consumed or produced (e.g. plugin descriptors, handler shapes) so initialization fails fast on a malformed structure instead of surfacing as a confusing downstream error. The same generic-factory approach would extend to **dynamic validation inside handlers** — a reusable factory for validating expected values out of request `body`/`params`, rather than every handler hand-rolling its own checks. Supersedes the previously-declined "plugin type notations" idea (a static/compile-time contract); this is a runtime validation mechanism instead.
- **`run()` startup error handling** — done (2026-09-10): considered switching to a callback-based startup signature, decided against it — `run()` is already awaited/chained everywhere (examples, tests), and a callback would change that call shape for every existing caller. Instead, kept `run()` Promise-based and fixed the actual bug: the server's `'error'` event (e.g. `EADDRINUSE`) now rejects the returned `Promise` instead of leaving it unsettled forever. All `example/*/index.js` entry points were updated to `.catch(...)` the startup call and `process.exit(1)` on failure. See `lib/server-based.js` (`runServerBased`) and [server-based.md](../api/server-based.md).
